# نورستان — گزارش مرحلهٔ دوم، ۱۳ بند

**تاریخ: ۲۰۲۶/۰۹/۲۶ · تغییرات محلی روی `arena/01a0da07-noorestan`**

کد و آزمون‌های محلی آماده‌اند، اما **پذیرش انتهابه‌انتهای محیط واقعی کامل نیست**: نشانی عمومی بک‌اند/تنظیمات سرویس پیامک تحویل نشده، تراکنشی روی خود سندباکس زرین‌پال انجام نشده و منبع یا API بازی خارجی برای دونفره‌کردن آن موجود نیست. این موارد با آزمون شبیه‌سازی‌شده جایگزین یا «انجام‌شده» اعلام نمی‌شوند. نشست GitHub بسته است؛ هیچ push یا PR تازه‌ای انجام نشده است.

عدد قدیمی **۲۱۱۸/۰** مربوط به پیش از حذف ورود مهمان/OTP محلی/مدیر محلی است و نتیجهٔ نسخهٔ فعلی نیست. `_tests.js` باقی مانده است؛ اجرای `LEGACY_TESTS=1 node _harness.js` قراردادهای بازنشسته را نیز اجرا و روی نبود MiniServer متوقف می‌شود. آزمون‌های جایگزین امنیت، سرور واقعی را هدف می‌گیرند. هارنس دیگر خطای uncaught را با کد خروج موفق پنهان نمی‌کند. این گزارش ادعا نمی‌کند تمام گزاره‌های تاریخی هنوز معادل مستقیم دارند.

### پوشش مهم امنیت و شبکه

- هویت پایدار از سرور، نه `userId` ادعایی؛ توکن جعلی رد می‌شود؛ اتصال بی‌احراز هویت روم نمی‌سازد.
- توکن مدیر جای توکن کاربر و بالعکس پذیرفته نمی‌شود؛ سوکت کاربر حتی با پیام hello دوم به نقش مدیر تبدیل نمی‌شود.
- دست‌کاری `isAdmin` دسترسی مدیریت نمی‌دهد؛ کاربر وارد پنل نمی‌شود و مدیر وارد صفحهٔ عادی نمی‌شود؛ reload مدیر دوباره تأیید می‌شود؛ انقضای **سمت کلاینت** ورود دوباره می‌خواهد.
- سه کد نادرست، OTP را می‌سوزاند؛ همان کد بعداً پذیرفته نمی‌شود؛ کد در پاسخ HTTP برنمی‌گردد.
- کاربر مسدود/حذف‌شده و توکن logoutشده رد می‌شوند؛ logout، سوکت‌های متعلق به همان توکن را می‌بندد.
- ورود دیرهنگام به دوز، تماشاچی با snapshot همان صفحه است؛ چت تماشاچی می‌رسد و خروجش بازی را صفر نمی‌کند.
- خروج میزبان، دور را لغو و میزبانی را منتقل می‌کند؛ خروج بازیکن غیرمیزبان در میانهٔ اسم‌فامیل هم دور را لغو می‌کند.
- دو ورود هم‌زمان به آخرین جای روم: دقیقاً یک بازیکن و یک تماشاچی؛ آغاز مجدد از غیرمیزبان رد می‌شود.
- فایل سرور، پرداخت، داده‌ها، تست‌ها و `.git` از وب عمومی ۴۰۴ می‌گیرند.
- هشت callback هم‌زمان پرداخت، replay پشت‌سرهم و راه‌اندازی مجدد فقط یک بار اعتبار می‌دهند؛ مبلغ از سفارش ذخیره‌شده می‌آید؛ NOK، OK جعلی، timeout و موفقیت بدون reference اعتبار نمی‌دهند.
- شکست نوشتن دفتر، مالکیت حافظه‌ای ایجاد نمی‌کند؛ حساب دیگر مانده را به ارث نمی‌برد؛ localStorage یا payload کلاینت نمی‌تواند پرداخت غیرفعال سرور را فعال کند.
- فوکوس سودوکو پس از ورود عدد حفظ می‌شود؛ تکمیل دوم هیچ تغییر مجددی در سکه، XP و آمار ایجاد نمی‌کند.

### اصلاحات پیدا‌شده حین آزمون

- `Admin.confirmServer/render`: قطع درخواست در زمان reload دیگر با «توکن باطل» اشتباه نمی‌شود و باعث revoke ناخواستهٔ نشست مدیر نمی‌شود؛ پاسخ کهنه نیز نشست تازه را خارج نمی‌کند.
- `Net.openWS`: پیام/open/retry سوکت قبلی روی اتصال تازه اثر نمی‌گذارد.
- `AyahEmbed.cleanup`: خروجی fullscreen پس از تکمیل درخواست درحال‌اجرای ورود، پاک‌سازی می‌شود؛ قاب در خروج حذف می‌شود.
- `Session.logout`: مسیر `#admin` به `#home` برمی‌گردد تا reload بعدی دوباره صفحهٔ مدیریت را تحمیل نکند.
- `sw.js`: GETهای `/api/`، از جمله callback درگاه، اصلاً intercept نمی‌شوند؛ پاسخ `no-store/private` قابل ذخیره نیست.

## راه‌اندازی برای آزمون واقعی بعدی

۱. برنامه و API/WS را روی **یک origin عمومی HTTPS، از ریشهٔ دامنه** سرو کنید؛ این نسخه تنظیم URL دلخواه در مرورگر کاربر ندارد. GitHub Pages به‌تنهایی Node/SMS/پرداخت را اجرا نمی‌کند. اگر بک‌اند موجود جداست، پروکسی هم‌خاستگاه لازم است؛ URL مرورگر نباید localhost باشد.

۲. متغیرهای محیطی سرور را در محیط امن میزبان تنظیم کنید؛ نه در HTML، نه در Git و نه در پیام گفتگو:

| متغیر | کاربرد |
|---|---|
| `HOST=0.0.0.0` و `PORT` | bind و پورت Node؛ پشت پروکسی، دسترسی مستقیم را محدود کنید. |
| `NOOR_DATA` | مسیر پایدار و خصوصی فایل حساب‌ها؛ مسیر پیش‌فرض `noorestan-data.json` است. |
| `NOOR_ADMIN_PASS` | رمز مدیریت سرور؛ بدون آن ورود مدیریت غیرفعال است. |
| `NOOR_SMS_KEY` و `NOOR_SMS_DEVICE` | تنظیمات واقعی textbee؛ مقدار در مرورگر ارسال/نگهداری نمی‌شود. |
| `NOOR_PAYMENTS=sandbox` | فعال‌سازی صریح پرداخت آزمایشی؛ پیش‌فرض غیرفعال، live پیاده نشده است. |
| `NOOR_PUBLIC_URL=https://your-domain.example` | origin برگشت عمومی و HTTPS؛ `.example` در این سطر فقط مثال است. |
| `NOOR_ZARINPAL_MERCHANT` | UUID مخصوص سندباکس در صورت نیاز؛ UUID پیش‌فرض آزمایشی در کد هست و پذیرندگی واقعی نیست. |

`NOOR_SMS_ENDPOINT` در تست‌ها فقط به فرستندهٔ ساختگی محلی اشاره می‌کند؛ آن تنظیم تست را وارد استقرار واقعی نکنید. بک‌اند باید ترافیک Upgrade وب‌سوکت را نیز از پروکسی دریافت کند. محدودیت‌های IP فعلی از آدرس سوکت استفاده می‌کنند؛ پشت پروکسی ممکن است کاربران یک IP مشترک دیده شوند و پیش از استفادهٔ پرترافیک باید سیاست نرخ در پروکسی/سرور بازبینی شود.

۳. دفتر پرداخت در `NOOR_DATA + '.payments.json'` نوشته می‌شود: **تک‌پردازه**، بدون cluster/چند worker یا نوشتن هم‌زمان چند ماشین. دیسک پایدار، حق دسترسی محدود و پشتیبان هر دو فایل لازم است. نشست‌ها حافظه‌ای‌اند؛ restart سرور ورود دوباره می‌خواهد. این پیاده‌سازی کیف پول بانکی، حسابداری تولیدی یا پذیرندگی live نیست.

۴. پس از تنظیم دامنه، یک حساب تازه با **پیامک واقعی** و یک خرید موفق و لغوشده در **خود سندباکس رسمی** انجام دهید؛ callback عمومی، رسیدها، reload، replay و اتصال دستگاه دوم را بررسی کنید. تا قبل از آن، نتیجهٔ این مرحله «آزمون محلی موفق» است، نه تأیید عملیاتی سرویس‌دهنده.

۵. برای دونفرهٔ واقعی بازی خارجی، سورس قابل تغییر یا API مستند شامل شناسهٔ جلسه، بازیکن، ورودی‌ها و همگام‌سازی وضعیت لازم است. ساخت روم میزبان یا تغییر قاب به‌تنهایی بازی داخلی را چندنفره نمی‌کند. قفل افقی روی iOS/مرورگرهای فاقد پشتیبانی تضمین‌پذیر نیست؛ پیام چرخاندن دستی/بازکردن جداگانه باقی است.
